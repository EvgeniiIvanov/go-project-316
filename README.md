## Установка

Клонируйте репозиторий и соберите бинарник:

```bash
git clone https://github.com/EvgeniiIvanov/go-project-316.git
cd go-project-316
make build
```

Бинарник появится в `bin/crawler`. Зависимости подтягиваются автоматически через `go.mod`, переменные окружения не требуются.

## Использование

Утилита обходит сайт начиная с переданного URL, следует по ссылкам в пределах того же хоста и выводит отчёт в формате JSON.

```bash
./bin/crawler https://example.com
```

Доступные флаги:

```
--depth int          максимальная глубина обхода, 0 значит только корневая страница (default: 10)
--retries int        количество повторов при неудачном запросе (default: 1)
--delay duration     фиксированная задержка между запросами, например 200ms, 1s (default: 0s)
--rps float          целевое количество запросов в секунду; если задан (>0), имеет приоритет над --delay: CLI сам переводит его в задержку (1s/rps) перед запуском обхода (default: 0, то есть не используется)
--timeout duration   таймаут запроса, например 5s, 15s (default: 15s)
--user-agent string  заголовок User-Agent для запросов (default: не задан)
--workers int        количество параллельных воркеров (default: 4)
--indent             форматировать JSON с отступами
--debug              логировать каждый HTTP-запрос в stderr: метод, URL, время начала, результат (статус или ошибка) и длительность
```

`--debug` не влияет ни на отчёт, ни на его формат: строки лога пишутся в stderr, а не в stdout, поэтому JSON, выводимый в stdout, остаётся пригодным для перенаправления в файл или другую программу без изменений. Каждая строка выглядит примерно так:

```
[DEBUG] 2024-06-01T12:34:56Z GET https://example.com/ -> 200 (123.456ms)
[DEBUG] 2024-06-01T12:34:57Z HEAD https://example.com/broken -> error: dial tcp: connection refused (45.2ms)
```

`--delay` ограничивает частоту HTTP-запросов глобально для всего процесса обхода, а не по отдельности для каждого воркера: сколько бы горутин ни работало параллельно, интервал между любыми двумя последовательными запросами не будет меньше заданного. Библиотека (`crawler.Options`) знает только про `Delay`; `--rps` — это удобство CLI, которое перед запуском переводится в эквивалентную задержку (`1s / rps`) и подставляется вместо `--delay`, если `--rps` больше нуля. Если оба параметра равны нулю (или не заданы), обход не замедляется.

`--retries` задаёт количество дополнительных попыток для одного запроса (страницы или проверяемой ссылки) после первой неудачи. Повтор выполняется только для временных ошибок:

- сетевой сбой (запрос не дошёл до сервера или не вернул ответ);
- HTTP 429 (Too Many Requests);
- любой код 5xx (500, 502, 503, 504 и т.д.).

Любой другой код ответа (например, 404 или 403) считается окончательным результатом и не повторяется, даже если остались доступные попытки. Между попытками выдерживается фиксированная ненулевая пауза, чтобы не создавать всплеск запросов; отмена контекста немедленно прерывает как ожидание паузы, так и саму попытку. В отчёте (включая список битых ссылок) фиксируется результат только последней попытки: если после `--retries` повторов запрос так и не увенчался успехом, страница помечается как `error`, а ссылка — как битая; если попытка в итоге увенчалась успехом, результат считается успешным независимо от того, сколько попыток этому предшествовало.

Пример с настройкой глубины и количества воркеров:

```bash
./bin/crawler --depth 3 --workers 10 --indent https://example.com
```

Пример с ограничением скорости по RPS:

```bash
./bin/crawler --rps 5 https://example.com
```

Помимо ссылок и SEO-данных, для каждой страницы в отчёте собирается поле `assets` — список статических ресурсов, на которые страница ссылается: изображения (`<img src>`), скрипты (`<script src>`) и стили (`<link rel="stylesheet" href>`). Каждый элемент имеет вид:

```json
{
  "url": "https://example.com/static/logo.png",
  "type": "image",
  "status_code": 200,
  "size_bytes": 12345,
  "error": ""
}
```

`type` принимает значения `image`, `script` или `style`. Размер (`size_bytes`) берётся из заголовка `Content-Length`, если сервер его прислал; иначе он вычисляется по фактически полученному телу ответа. Если размер определить не удалось (например, тело не удалось прочитать целиком), `size_bytes` равен `0`, а причина указывается в `error`. Ответ с кодом ≥ 400 также фиксируется как ошибка ассета с соответствующим `status_code` и текстом в `error`. Как и проверка ссылок, загрузка ассетов кэшируется по полному URL за весь обход: один и тот же ассет, встречающийся на нескольких страницах, запрашивается у сервера только один раз, а во всех страницах отчёта фигурируют одинаковые данные.

## Формат отчёта

Ниже — эталонный пример отчёта, с которым сверяется вывод утилиты (см. `TestReport_JSONMatchesReferenceSchema`):

```json
{
  "root_url": "https://example.com",
  "depth": 1,
  "generated_at": "2024-06-01T12:34:56Z",
  "pages": [
    {
      "url": "https://example.com",
      "depth": 0,
      "http_status": 200,
      "status": "ok",
      "error": "",
      "seo": {
        "has_title": true,
        "title": "Example title",
        "has_description": true,
        "description": "Example description",
        "has_h1": true
      },
      "broken_links": [
        {
          "url": "https://example.com/missing",
          "status_code": 404,
          "error": "Not Found"
        }
      ],
      "assets": [
        {
          "url": "https://example.com/static/logo.png",
          "type": "image",
          "status_code": 200,
          "size_bytes": 12345,
          "error": ""
        }
      ],
      "discovered_at": "2024-06-01T12:34:56Z"
    }
  ]
}
```

Все перечисленные ключи присутствуют в отчёте всегда, даже если их значение пустое (пустая строка, `0` или пустой массив `[]`): например, `error` есть у каждой страницы, даже когда обход прошёл без ошибок. Пустой список `broken_links` или `assets` сериализуется как `[]`, а не как `null`.

Поля верхнего уровня:

- `root_url` — URL, с которого начался обход.
- `depth` — заданная максимальная глубина обхода.
- `generated_at` — момент формирования отчёта, ISO8601/RFC3339 (UTC).
- `pages` — список посещённых страниц.

Поля страницы (`pages[]`):

- `url` — адрес страницы.
- `depth` — глубина, на которой страница была обнаружена (0 — корневая).
- `http_status` — код ответа сервера при загрузке страницы (0, если запрос не дошёл до сервера).
- `status` — `"ok"` или `"error"`.
- `error` — текст ошибки при загрузке самой страницы; пустая строка при успехе.
- `seo` — SEO-сигналы, см. ниже.
- `broken_links` — список битых ссылок, найденных на странице (может быть пустым `[]`).
- `assets` — список статических ресурсов страницы (может быть пустым `[]`).
- `discovered_at` — момент, когда страница была поставлена в очередь обхода, ISO8601/RFC3339 (UTC).

Поля `seo`:

- `has_title`, `has_description`, `has_h1` — присутствовал ли соответствующий тег в HTML.
- `title`, `description` — декодированный и очищенный от лишних пробелов текст тега; пустая строка, если тег не найден.

Поля элемента `broken_links[]`:

- `url` — адрес битой ссылки.
- `status_code` — код ответа сервера (0 при сетевой ошибке).
- `error` — текст ошибки (например, `"Not Found"` или текст сетевого сбоя).

Поля элемента `assets[]` описаны выше, в разделе про ассеты.

Флаг `--indent` влияет только на форматирование JSON (отступы и переносы строк) и никак не меняет ни состав, ни порядок ключей, ни значения (см. `TestReport_IndentJSONOnlyAffectsFormatting`). CLI печатает JSON как есть, без какого-либо текста до или после него (не считая завершающего перевода строки).
